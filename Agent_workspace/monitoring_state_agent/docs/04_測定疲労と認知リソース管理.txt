# 測定疲労と認知リソース管理

システムは、ユーザーを「無限にタスクを処理できる機械」ではなく、「有限のリソースを持つ生物」として扱う。
測定を持続させるためには、**測定疲労（行為への飽き・疲れ）**と**認知リソース（意志力の残量）**という2つの変数を独立して管理し、それらに基づいてシステムの振る舞いを動的に調整する必要がある。

---

## 1. 測定疲労 (Measurement Fatigue)

ユーザーが「自分の状態を観測・記録する」という行為そのものに対して感じる心理的負担や飽きの蓄積。

### 1.1 変数定義
#### `measurement_fatigue_level` (0.0 - 1.0)
-   **意味**: 測定行為に対する現在の疲労度。
    -   `0.0`: 全く疲れていない（測定への意欲が高い）。
    -   `1.0`: 限界（測定を即座にやめたい、嫌悪感）。
-   **蓄積要因**:
    -   **測定時間**: 測定モードが長く続くほど蓄積する。
    -   **入力頻度**: 手動入力（チェックリスト等）の要求が多いほど急激に上昇する。
    -   **介入頻度**: システムからの通知が多いと「監視されている」感覚が強まり上昇する。
-   **回復要因**:
    -   **非測定状態**: 測定モードを解除し、解放されている時間。

### 1.2 数理モデル（ドラフト）
疲労レベルの時間発展は以下の簡易モデルで近似される。

```python
if is_measurement_mode:
    # 測定中は徐々に疲労が蓄積
    fatigue[t+1] = fatigue[t] + (base_accumulation_rate + input_cost * input_count) * dt
else:
    # 非測定中は回復
    fatigue[t+1] = fatigue[t] - measurement_fatigue_recovery_rate * dt
```

### 1.3 閾値とシステム介入
疲労レベルに応じて、システムはユーザーへの要求レベルを段階的に引き下げる。

| 疲労レベル | 状態 | システムの挙動（介入） |
| :--- | :--- | :--- |
| **0.0 - 0.3** | 快適 | **通常モード**: 全てのデータを記録。詳細なチェックリストを提示。 |
| **0.3 - 0.6** | 軽度疲労 | **省力モード**: 必須項目のみ入力要求。通知頻度を少し下げる（`adjust_notification_frequency_by_fatigue`）。 |
| **0.6 - 0.8** | 警告域 | **ミニマルモード**: センサーのみ記録。ユーザー入力はYes/Noのみ。休憩を推奨。 |
| **0.8 - 1.0** | 危険域 | **測定停止推奨**: 「測定を終了して休みましょう」と提案。強制的な介入停止。 |

## 2. 認知リソース (Cognitive Resource)

自我消耗 (Ego Depletion) 理論に基づく、意志決定、感情抑制、複雑なタスク遂行のために使用される有限の精神的エネルギー。

### 2.1 変数定義
#### `current_cognitive_resource_level` (0.0 - 1.0)
-   **意味**: 現在利用可能なウィルパワー（意志力）の残量。
    -   `1.0`: 満タン（起床直後や十分な休息後）。
    -   `0.0`: 枯渇（判断能力の低下、衝動的行動）。
-   **測定能力への影響**:
    -   リソースが低下すると、`user_measurement_capability`（自分を客観視する能力）も低下する。
    -   **重要**: 疲れてくると「自分が疲れていること」を正確にモニタリングできなくなる。

### 2.2 減衰ロジック
#### `estimate_cognitive_depletion`
以下の要素を入力として、リソース消費量を推定する関数。

1.  **タスク負荷**: `task_intensity * duration`
    -   集中を要する作業や、嫌な作業は消費が激しい。
2.  **環境エントロピー**: `room_entropy_s`
    -   散らかった部屋（視覚的ノイズ）は、常にバックグラウンドでリソースを消費させる（抑制コスト）。
3.  **感情労働**:
    -   社会的状態におけるストレス（対人緊張）もリソースを消費する。

### 2.3 回復ロジック
-   **睡眠**: 最大のリソース回復源。
-   **休憩 (Rest)**: `time_since_last_break` がリセットされるタイミングで少量回復。
-   **セーバリング (Savoring)**: 感謝やポジティブな感情の想起による回復（実験的実装）。
-   **糖分摂取**: （生理学的モデルとして考慮するが、過剰摂取リスクがあるため慎重に扱う）。

## 3. ドロップアウト予測 (Dropout Prediction)

「ユーザーが測定やタスクを放棄してしまう確率」を事前に予測し、失敗する前に手を打つための機能。

### 3.1 予測モデル
#### `predicted_dropout_probability`
以下の変数を説明変数とするロジスティック回帰的なモデル（またはルールベース判定）。

$$ P(dropout) = \sigma( w_1 \cdot \text{Fatigue} + w_2 \cdot (1 - \text{Resource}) + w_3 \cdot \text{Stress} ) $$

-   **Fatigue**: `measurement_fatigue_level` (測定そのものが嫌になる)
-   **Resource**: `current_cognitive_resource_level` (やる気がなくなる)
-   **Stress**: `discrepancy_score` (主観と客観の乖離による違和感)

### 3.2 予測に基づく予防的介入
確率が高まった場合、システムは「タスクの完了」よりも「ユーザーの継続」を優先する。

1.  **ハードルを下げる**:
    -   「あと2時間」の予定を「あと15分」に短縮提案。
    -   難しいタスクを代替タスク（単純作業）に置き換え。
2.  **回復を促す**:
    -   「認知リソースが低下しています。5分間目を閉じてみませんか？」
3.  **測定の一時停止**:
    -   「測定疲れが見られます。午後は記録をオフにして自由に過ごしましょう。」

---

## 結論
このモジュールは、ユーザーを管理するのではなく、**ユーザーのリソース枯渇を防ぐセーフティネット**として機能する。
測定データが途切れたり、タスクが未完了になったりしても、それは「ユーザーの失敗」ではなく「システムのリソース管理（見積もり）の甘さ」として処理し、次回の予測モデルにフィードバックする。
