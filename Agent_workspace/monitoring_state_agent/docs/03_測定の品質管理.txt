# 測定の品質管理

測定状態にあるとしても、そのデータが信頼できるものでなければ、エントロピーの計算や危篤状態の判定、ひいては組織エッジの維持に悪影響を及ぼす。
monitoring_state_agentは、単なるデータの有無だけでなく、信号の「質」と「文脈」を評価し、信頼性の高いモニタリング基盤を提供する。

## 1. 品質指標 (Measurement Quality Metrics)

### 1.1 current_measurement_quality_score (CMQS)
測定データの総合的な信頼性を 0.0 〜 1.0 のスコアで表現する動的な指標。

-   **定義**: 現在の測定データの品質スコア。
-   **計算式 (概念モデル)**:
    $$CMQS = w_1(S_{noise}) + w_2(R_{loss}) + w_3(C_{device}) + w_4(A_{context})$$
    -   $S_{noise}$: 信号対雑音比 (Signal-to-Noise Ratio) から算出されるスコア。体動ノイズや装着ズレによる異常値を評価。
    -   $R_{loss}$: データ欠損率 (Data Loss Rate)。期待されるサンプリング数に対する実際の取得数の比率。
    -   $C_{device}$: デバイス状態スコア。バッテリー残量、Bluetooth信号強度 (RSSI)、装着センサー (Contact Sensor) の状態。
    -   $A_{context}$: 文脈適合度。現在の活動量 (Activity Level) に対して、取得された心拍数などが生理学的に妥当な範囲内か。
-   **閾値**:
    -   `minimum_reliability_for_valid_record` (例: 0.7): この値を下回る期間のデータは、公式な記録（エントロピー計算や医療的判断）には使用せず、「参考値」としてフラグ付けする。
-   **用途**:
    -   **信頼性アラート**: スコアが低下した場合、「スマートウォッチの装着位置を直してください」等の具体的な改善指示をユーザーに通知する。
    -   **自動補正の可否判定**: スコアが高い場合は欠損値を線形補間するが、低い場合は補間を行わず「測定不能」として扱う。

### 1.2 last_valid_measurement_timestamp
-   **定義**: 最後に `CMQS >= minimum_reliability_for_valid_record` を満たす「有効（Valid）」な測定データパケットが取得された正確な時刻 (ISO 8601)。
-   **重要性**: 測定状態の継続性を判定する際の「最終生存確認時刻」として機能する。ノイズだらけのデータが送られてきているだけでは、この時刻は更新されない。

## 2. 継続性判定ロジック (Continuity Logic)

測定は連続的であることが理想だが、現実には通信断絶や一時的なデバイスの取り外しが発生する。システムはこれを許容しつつ、どの時点で「測定状態が解除された」とみなすかの明確な基準を持つ必要がある。

### 2.1 measurement_gap_tolerance_seconds
-   **定義**: 有効な測定データが途切れても、即座に測定モードを終了せず「一時的な中断」として許容する猶予時間（タイムアウト値）。
-   **設定値の目安**:
    -   測定モード中: 300秒 (5分) 〜 600秒 (10分)
    -   ※ アクティビティの種類によって動的に変動させる場合もある（例：水泳中は通信が切れやすいため長めに設定）。
-   **判定プロセス**:
    1.  現在時刻 ($T_{now}$) と最終有効時刻 ($T_{last}$) の差分 $\Delta t$ を計算。
    2.  $\Delta t \le tolerance$: 「測定中（接続不安定）」ステータス。ユーザーには警告を出さないか、軽微な通知にとどめる。
    3.  $\Delta t > tolerance$: 「測定状態解除（ドロップアウト）」と判定。
        -   組織エントロピー計算における「エッジ」の切断処理を開始する。
        -   ユーザーへ「測定が停止しました。再開しますか？」と確認通知を送る。

### 2.2 validate_measurement_continuity (関数)
-   **入力**: 最終測定時刻 ($T_{last}$), 現在時刻 ($T_{now}$), 許容時間 ($Tolerance$), 現在の活動状態 ($Activity$)
-   **出力**:
    -   `is_continuous`: Boolean (継続しているか)
    -   `state_status`: Enum (Active, Unstable, Lost)
-   **ロジック**:
    単なる時間経過だけでなく、文脈も考慮する。例えば、「就寝中」と判定されている間は、センサーが一時的にズレても許容時間を長くする（ユーザーを起こさないため）などの調整を行う。

## 3. センサーデータの取り扱い

### 3.1 異種センサーの統合 (Sensor Fusion)
複数のデバイス（例：スマートウォッチ + スマートリング + 環境センサー）を使用している場合、`device_connection_status_map` を用いて各デバイスの状態を管理する。

-   **優先順位**: 同じ指標（例：心拍数）が複数のデバイスから取得できる場合、CMQSが高い方のデータを採用する。
-   **補完関係**: スマートウォッチで心拍数、環境センサーで室温を取得し、これらを統合して「不快指数と心拍数の相関」を分析可能な単一のレコードとする。

### 3.2 ノイズフィルタリングと順化 (Habituation)
-   **sensor_habituation_factor**: センサー装着に対する身体的・心理的な慣れ（順化）の度合い (0.0 - 1.0)。
    -   導入初期は装着自体がストレスとなり、バイタルデータ（心拍数や皮膚コンダクタンス）が高めに出る傾向がある。
    -   システムは順化係数を用いて、初期のベースラインを高めに設定し、慣れるに従って標準的なベースラインへと補正していく。これにより、「装着ストレス」を「異常検知」と誤判定するのを防ぐ。

## 4. エラーハンドリングとユーザーフィードバック

### 4.1 測定品質低下時のアクション
品質スコア (CMQS) が低下した際、原因に応じた適切なフィードバックを行う。

-   **ケースA: 装着ズレ (Contact Loss)**
    -   検知: PPG信号の振幅低下、接触センサーのOFF。
    -   アクション: 「ウォッチが緩んでいるようです。締め直してください」
-   **ケースB: バッテリー切れ (Low Battery)**
    -   検知: バッテリーレベル < 5%。
    -   アクション: 「バッテリー残量がわずかです。充電してください」
-   **ケースC: 通信不安定 (Signal Weak)**
    -   検知: RSSI低下、パケットロス増加。
    -   アクション: 「スマホとの距離が離れています」

### 4.2 ドロップアウト予測 (Predictive Dropout)
-   **predicted_dropout_probability**: 現在の負荷、バッテリー残量、測定疲労度 (`measurement_fatigue_level`) から、直近（例：1時間以内）に測定が中断される確率を予測。
-   **予防措置**: 確率が高い場合、早めに「休憩」や「充電」を提案し、意図しない測定停止を防ぐ。
