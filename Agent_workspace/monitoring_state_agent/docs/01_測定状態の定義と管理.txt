# 測定状態の定義と管理

## 1. 測定状態 (Measurement State) の詳細定義

### 1.1 定義
「測定状態」とは、システムにおいてユーザーが「自身の状態を能動的かつ継続的に観測・記録している」と定義される特定の時間帯を指します。
この状態は、単なるデータ収集プロセスではなく、ユーザーが自己を客観視し、メタ認知を働かせている**「自己管理モード」**として位置づけられます。

### 1.2 構成要素
測定状態は以下の要素によって構成・維持されます：

1.  **センサーによる客観的測定 (Objective Monitoring)**
    *   **対象**: 脈拍、血圧、活動量、環境データ（温度、湿度、CO2濃度など）。
    *   **動作**: バックグラウンドで自動的に継続実行される。
    *   **目的**: ユーザーの主観に依存しない「事実」を記録し、乖離検知のベースラインとする。

2.  **チェックリストによる主観的測定 (Subjective Monitoring)**
    *   **対象**: 気分、意欲、身体的感覚（痛み、違和感）、思考内容（想起）。
    *   **動作**: 開始時、終了時、およびセッション中の特定タイミングでユーザーに入力を求める。
    *   **目的**: センサーでは捉えきれない内的体験を言語化・数値化し、認知リソースを「自己観察」に向ける。

3.  **システムによるフィードバック (System Feedback)**
    *   **動作**: 測定データに基づき、状態の乖離や異常（危篤状態の兆候）を検知して通知する。
    *   **目的**: ユーザーの気づきを促し、行動変容（休憩、深呼吸など）をサポートする。

## 2. 測定負荷の管理 (Measurement Load Management)

測定行為そのものが認知リソースを消費し、精神的負担（測定疲労）となる可能性があります。
持続可能な自己管理のために、システムは厳格な負荷管理を行います。

### 2.1 推奨リミット
*   **1日の推奨測定時間**: `measurement_limit_daily_min` (6時間) 〜 `measurement_limit_daily_max` (8時間)
    *   **根拠**: 人間が高い集中力とメタ認知を維持できる限界時間に基づく。これを超えると「測定疲れ」によるデータ品質の低下や、強迫的な自己監視（過覚醒）のリスクが高まる。
*   **週の推奨測定頻度**: `measurement_days_weekly_min` (3日) 〜 `measurement_days_weekly_max` (6日)
    *   **根拠**: 休息日（非測定日）を設けることで、測定というプレッシャーから解放される時間を確保し、長期的な継続率を高める。

### 2.2 制限超過時の対応
*   **アラート通知**: 日次上限（8時間）に達した時点で、`measurement_limit` 通知ルールが発火。「本日の測定時間が推奨上限に達しました。非測定モードへの移行を推奨します」と通知される。
*   **強制終了はしない**: ユーザーの自律性を尊重し、システムによる強制的な測定停止は行わないが、推奨上限を超えた記録は「過剰測定」としてフラグ付けされ、分析時に考慮される場合がある。

## 3. 非測定状態 (Non-Measurement State)

### 3.1 定義と目的
測定を行わない時間帯。システムは能動的なデータ収集や通知を停止または最小限にします。
*   **目的**:
    *   **心理的解放**: 「常に監視されている/しなければならない」という緊張感を解く。
    *   **リソース回復**: 認知リソースを回復させ、次回の測定セッションに向けた活力を養う。
    *   **純粋な体験**: 記録することを意識せず、活動そのものに没頭する（フロー体験）時間を確保する。

### 3.2 挙動の違い
| 機能 | 測定状態 (Measurement State) | 非測定状態 (Non-Measurement State) |
| :--- | :--- | :--- |
| **センサー記録** | 高頻度 / 常時記録 | 低頻度 / 必要最小限（または停止） |
| **チェックリスト** | 定期的に提示（開始/終了/セッション中） | 提示しない（ユーザーが自発的に開く場合を除く） |
| **通知・介入** | 詳細なフィードバック、行動提案あり | 緊急時（危篤状態検知）のみ通知 |
| **データ扱い** | 公式な記録として集計・分析対象 | 参考値として扱い、集計からは除外（オプション） |

## 4. 予定オブジェクトとしての測定モード

### 4.1 実装モデル
測定モードは、タスクの属性（フラグ）ではなく、独立した**「予定オブジェクト (Scheduled Event)」**としてデータモデル上で扱われます。

*   **Type**: `measurement_session`
*   **Template**: システム定義の暗黙的テンプレート（`isSystemTemplate: true`）を使用。
*   **Properties**:
    *   `scheduledStart` / `scheduledEnd`: 測定を行う予定の時間枠。
    *   `actualStart` / `actualEnd`: 実際に測定を行った時間（実行記録）。
    *   `status`: `scheduled` (予定), `in_progress` (測定中), `completed` (完了), `skipped` (スキップ)。

### 4.2 ユーザーインターフェース (UI) と体験
*   **タイムライン表示**: カレンダー上で他のタスク（会議、作業など）とは異なる視覚表現（例：背景色、太枠）で、「8:00-16:00 測定モード」のような時間帯ブロックとして表示される。
*   **階層構造の表現**: 測定モードのブロック内に、個別のタスク（「資料作成」「会議」など）が配置されるような視覚的メタファーを採用することで、「このタスクは測定モード下で行われている」ことを直感的に理解させる。
*   **操作**: ユーザーは「測定を開始する」ボタンを押すのではなく、タイムラインに「測定モード」ブロックを配置（または既存の予定を確認）することで、その時間の測定意思を表明する。

### 4.3 自動化されたインタラクション
*   **開始時**: 予定時刻になると、システムは自動的に測定準備（センサー接続確認など）を行い、「測定モードの時間です」と通知する。
*   **終了時**: 終了時刻になると、一日の振り返り（終了時チェックリスト）を促し、測定モードからの離脱をサポートする。
