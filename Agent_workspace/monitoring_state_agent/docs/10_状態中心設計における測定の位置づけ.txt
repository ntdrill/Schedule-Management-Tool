# 状態中心設計における測定の位置づけ

本システムにおいて、測定は「完了すべきタスク」ではなく「維持すべき状態」として再定義される。
このパラダイムシフトにより、ユーザーの認知負荷を最小化し、持続可能な自己管理を実現する。

---

> **バージョン対応について**
> - **v1**: 測定ON/OFFトグルによるシンプルな切り替え方式を採用。タイムライン配置機能は含まれない。
> - **v2以降**: タイムラインUIへの測定状態ブロック配置を実装。

---

## 1. ユーザー体験の転換 (UX Paradigm Shift)

### 1.1 従来モデル: Task-Centric Monitoring
従来のヘルスケアアプリやタスク管理ツールにおける測定のアプローチ。
-   **操作**: ユーザーは「測定開始ボタンを押す」「ストップウォッチを止める」といった能動的なアクションを要求される。
-   **認知**: 測定は「やらなければならない作業（To-Do）」として認識され、完了すること自体が目的化しやすい。
-   **問題点**: 測定し忘れた時の罪悪感、開始操作の手間による離脱、断片的なデータ。

### 1.2 状態中心モデル: State-Centric Monitoring
本システムが採用するアプローチ。

**【v1の実装】**
-   **操作**: ユーザーはWatch/iPhoneのメイン画面で**[測定 ON/OFF]トグル**を操作する。
-   **認知**: 測定は「今この瞬間、自分を観測可能な状態にするか否か」のシンプルな選択。
-   **メリット**: タイムライン配置の学習コスト不要。即座に測定開始/終了が可能。

**【v2以降の実装】**
-   **操作**: ユーザーはタイムライン上に「**測定している状態 (Measurement State)**」というブロックを配置する。
-   **認知**: 測定は「その時間帯における自分のモード（在り方）」として認識される。
-   **意図**: 「この時間帯（例: 9:00-17:00）は、自分を観測可能な状態に保つ」という意思表示（コミットメント）。
-   **メリット**: 個別の開始・終了操作が不要。生活リズムの一部として測定が組み込まれる。

## 2. システムによる自動化プロセス (Automation Logic)

### 【v1の実装】
ユーザーが測定ON/OFFを切り替えると、`monitoring_state_agent`は以下のプロセスを実行する。

#### 2.1 センサーの制御 (Sensor Control)
-   **起動トリガー**: ユーザーが測定ONを選択した時点。
-   **動作**:
    -   HealthKitからの心拍数・HRV取得を開始。
    -   SwitchBot API経由で室温・湿度を取得。
-   **終了処理**: ユーザーが測定OFFを選択、またはバッテリー低下時に通常モードへ戻す。

#### 2.2 通知 (Notification)
-   測定ONのまま長時間経過した場合の確認通知。
-   対処行動中の経過時間通知。

### 【v2以降の実装】
ユーザーがタイムライン上に「測定状態」を配置すると、より高度な自動化を行う。

#### 2.1 センサーの自動制御 (Sensor Orchestration)
-   **起動トリガー**: 測定状態の開始時刻（`scheduledStart`）が到来、またはユーザーが「測定状態に入った」と確認した時点。
-   **動作**:
    -   連携デバイス（Apple Watch, Oura Ring等）に対し、高頻度サンプリングモードへの移行を要求。
    -   環境センサー（CO2, 温湿度）のデータ取得頻度を上げる。※CO2はv2以降
    -   バッテリー残量を確認し、長時間の測定に耐えられない場合は警告を発出。
-   **終了処理**: 測定状態の終了時刻、またはユーザーによる中断操作で、低電力モード（通常モニタリング）へ戻す。

#### 2.2 チェックリストの動的スケジューリング (Dynamic Checklist Scheduling)
-   **コンテキスト認識**: 測定状態の長さ、配置された時間帯（朝/昼/夜）、前後のタスク内容を分析。
-   **提示タイミング**:
    -   **開始時 (Entry)**: 「測定の準備はできていますか？（デバイス装着確認など）」
    -   **セッション中 (In-Session)**: 長時間の測定（例: 4時間経過）の場合、「集中力は続いていますか？」といった簡易チェックを挿入。
    -   **終了時 (Exit)**: 「このセッションでの気付きはありましたか？」といった振り返りを促す。
-   **負荷調整**: ユーザーの状態（`measurement_fatigue_level`）が高い場合、必須項目以外のチェックリストを自動的にスキップする。

#### 2.3 通知と介入のモード切替 (Notification Mode Switching)
-   **測定状態中 (Active Mode)**:
    -   **フィードバック**: 「心拍数が上昇しています、深呼吸しましょう」といったリアルタイムな生体フィードバックを有効化。
    -   **危篤状態アラート**: 閾値を超えた場合、即座に介入（リカバリータスク提案）を行う。※閾値判定はv2以降
    -   **詳細度**: データの詳細な変動や傾向を表示する。
-   **非測定状態中 (Passive Mode)**:
    -   **サイレント**: 緊急性の高いアラート（生命に関わるレベル）以外は通知を抑制。
    -   **休息優先**: 「測定してください」という通知自体を行わない。

## 3. UI表現 (User Interface Representation)

### 【v1の実装】

#### 3.1 トグルベースの測定管理
-   **Watch**: メイン画面に大きな[測定 ON/OFF]トグルボタン。
-   **iPhone**: ダッシュボードに同様のトグル＋設定画面。
-   **ログ閲覧**: iPhoneのHistory/Log画面で時系列表示。

### 【v2以降の実装】

#### 3.1 タイムライン表示
-   **カレンダービュー**: 通常の予定（会議、作業）と同様に、時間軸に沿ったブロックとして表示される。
-   **視覚的区別**: 測定状態のブロックは、背景色や枠線で明確に区別される（例: 薄い青色の背景）。
-   **重ね合わせ**: 「測定状態」という大きなブロックの上に、「会議」「作業」といった個別のタスクブロックが乗る（レイヤー構造）。

#### 3.2 状態の可視化
-   **アスタリスク型インジケータ**: 詳細な数値を羅列する代わりに、ユーザー状態・環境状態・社会的状態を統合した抽象的な図形を表示。
    -   形状や色が「整っている（青/緑）」か「乱れている（赤/オレンジ）」かを直感的に伝える。
-   **詳細の段階的開示 (Progressive Disclosure)**:
    -   通常時: シンプルなインジケータのみ。
    -   タップ時: 主要な指標（脈拍、CO2濃度など）を表示。
    -   詳細画面: すべてのログとグラフを表示。

---

この設計により、ユーザーは「測定ツールの操作」というマイクロマネジメントから解放され、「あるべき状態の維持」という本質的な目的に意識を向けることができる。v1ではシンプルなトグル操作から始め、v2以降でタイムラインベースの高度な自動化へ移行する。
