# 形式的スナップショット記述法 ガイドライン

作成日: 2026/01/02
適用範囲: データモデル設計、システム挙動定義

## 1. 背景と目的

本プロジェクトでは、極めて詳細かつ多層的なデータモデル（予定/実行分離、多層状態、測定モードなど）を定義している。しかし、これらを自然言語や従来のクラス図だけで表現しようとすると、以下の問題が発生する。

*   **意味論的ギャップ**: ドメイン知識の「深さ（ニュアンス）」が、実装コードに落とし込まれる過程で失われる。
*   **仕様の曖昧性**: 「評価する」と書くだけでは、「誰が、何を元に、どう評価し、結果をどこに置くか」が不明確なままになる。

この問題を解決するため、定義済みの**シンボル**と**演算子**を用いた「形式的記述（Formal Description）」を採用する。

## 2. なぜ形式的記述が支配的なのか

形式的記述が、自然言語や静的な図解よりも優れている（Dominantである）理由は以下の点にある。

### 2.1. 解釈の一意性 (Unambiguity)
自然言語は読み手に文脈補完を依存するが、論理式は依存しない。`A ≫ B` と書けば、Aの完了後にBが実行されることは絶対的である。これにより、設計者と実装者の間での認識齟齬を根絶する。

### 2.2. 検証可能性 (Verifiability)
記述が数式（関数合成）の形を取るため、ロジックの整合性を静的に検証できる。
*   入力型と出力型の不整合
*   副作用の抜け漏れ
*   条件分岐の網羅性
これらを実装前に「式のチェック」として発見できる。将来的には、この記述からテストケースを自動生成することも可能になる。

### 2.3. 本質の抽出 (Abstraction of Essence)
コードの「文法（Syntax）」や「定型句（Boilerplate）」に惑わされず、ドメインロジックの「核心（Core）」だけを抽出して議論できる。
「どの関数がどの変数を更新するか」というデータフローの骨格が剥き出しになるため、設計の欠陥が見えやすくなる。

## 3. 記述構文 (Syntax)

スナップショットは、以下の基本構文を持つ「1文の論理式」として記述する。

**基本形**:
`Context ≫ (Input ⫸ Function ⟼ Output) ≫ StateUpdate ∴ Result`

### 主要演算子

| シンボル | 名前 | 意味 | 用途 |
| :--- | :--- | :--- | :--- |
| `≫` | Sequence | 順次実行 | 時間的・論理的な順序を表す。前の処理が完了してから次へ進む。 |
| `⟼` | Assign | 代入・更新 | 関数の出力結果を、変数やオブジェクトのフィールドに束縛する。 |
| `⫸` | Pipeline | パイプライン | 前の処理結果や条件を、次の関数の入力やガード条件として渡す。 |
| `∴` | Result | 結論 | 一連のフローの結果として確定した状態遷移や、システムの最終的な判断。 |

## 4. 記述の原則 (Principles)

### 4.1. 完全性の原則 (Completeness)
暗黙の了解を許さない。関数が必要とする入力（辞書、現在時刻、定義データなど）は、全て引数として明示する。
*   Bad: `select_task(state)`
*   Good: `select_task(state, task_dictionary)`

### 4.2. 副作用の明示 (Explicit Side-Effects)
システムの状態が変化する箇所は、必ず `⟼` を用いて「どこが書き換わるか」を明記する。
*   `calc_negentropy(...) ⟼ room_entropy`

### 4.3. 関数型思考 (Functional Thinking)
システムを「状態変換関数の合成」として捉える。オブジェクト指向的な「メソッド呼び出し」ではなく、データが関数を通過して変容していく「フロー」として表現する。

### 4.4. トリガー・条件の明示 (Trigger & Condition)
ユースケースに「〜したら」「〜なら」が明示されている場合は、入力元または条件として式に含める。
未定義の入力・条件は `?_n` を使用し、**未整備**として明示する。

* 例: 「ユーザーがLog Stateを選択」→ `?_1` を入力元として導入
* 例: 「期待状態が選択されていれば」→ 条件 `?_2` を `⫸` で接続

## 5. ケーススタディ: 危篤検知ループ

以下は、この記述法を用いて定義された「危篤検知とフィードバック制御ループ」の例である。

`(↮(ꀴ, ꀔ) ⟼ ꀴ) ≫ (↖(ꀴ.subjective, ꀔ) ⟼ ꀏ) ≫ (↞(ꀴ, ꀏ, ህ) ⟼ ꀈ) ≫ ((ꀈ ?!= null) ⫸ (↬(ꀈ, ሡ) ⟼ ┃_rec) ≫ (↛(┃_rec, ꀊ) ⟼ ─_exec) ≫ (↪(ꀴ, ꀔ) ⟼ ─_exec.state_after) ≫ (↥(┃_rec.expected, ─_exec.state_after) ⟼ ─_exec.result) ≫ (↞(─_exec.state_after, ꀏ, ህ) ?= null ∴ ꀚ_restored))`

この式一つで、以下の仕様が厳密に定義されている。
1.  センサーデータによる状態更新 (`↮`)
2.  主観・客観乖離の数値化 (`↖`)
3.  乖離を考慮した危篤判定 (`↞`)
4.  異常時の介入（タスク生成 `↬` → 実行 `↛` → 記録 `↪` → 評価 `↥`）
5.  介入後の再判定による正常復帰の確定 (`∴ ꀚ_restored`)

## 6. 設計プロセスへの応用

この記述法は、トップダウンの設計（クラス図を描いてから詳細を詰める）ではなく、**ボトムアップの帰納的設計**を推奨する。

1.  具体的なユースケース（スナップショット）を大量に式として記述する。
2.  記述された式の中から、共通するパターンやデータ構造を発見する。
3.  発見されたパターンを、普遍的なクラス構造やメソッドとして定義する。

これにより、机上の空論ではない、実態に即した堅牢なデータモデルが構築される。
