## 資料準拠：docsフォルダの構成と内容

`docs`フォルダは4つのサブフォルダに分かれています。

### 1. UIとUXに関する決定
`UI設計方針_状態中心モデル.md`には、状態中心設計の基本方針が記載されています。ユーザーは「何をするか」ではなく「どのような状態でありたいか」のみを指定し、システムがタスクの選択や測定タイミング、チェックリストの提示を自動決定する設計です。UIはDAWライクな横スクロール型の並列トラック表示で、ユーザー状態、環境状態、社会的状態の3トラックを並列配置します。操作はデベロッパーが用意した状態プリセットをドラッグ&ドロップで配置する形です。

### 2. データモデルに関する決定
このフォルダには20以上の詳細な設計ドキュメントが含まれています。主要な内容は以下の通りです。

**予定と実行の分離**：予定オブジェクトは不変のスケジュール意図を表し、実行オブジェクトは実際の実行記録を表す別エンティティとして設計されています。一つの予定に対して複数の実行を記録可能で、タスクの中断と再開にも対応します。

**状態管理の三層構造**：ユーザー状態オブジェクト（現在の実際の状態）、状態履歴オブジェクト（過去の特定時点のスナップショット）、状態スキーマ（期待される状態の型定義）の三つが明確に区別されています。

**状態管理対象の一般化**：ユーザー状態（神経、臓器、筋肉、血圧、脈拍など）、環境状態（清潔度、換気、照明、温度、湿度、カビリスクなど）、社会的状態（対人接触頻度、孤独感、対人ストレスレベルなど）の三種類の状態を管理する設計です。各状態はsubjectTypeフィールドで区別され、基底スキーマと派生スキーマに分割されています。

**測定モード**：測定状態と非測定状態を区別し、測定推奨は1日6〜8時間、週3〜6回とされています。測定モードは独立した予定オブジェクトとして扱われ、その時間帯内で実行されたタスクの時間が測定時間として集計されます。

**危篤状態の検知とリカバリー**：ルールベースの自動判定とLLM APIによる判定を併用し、危篤状態が検知されるとリカバリータスクの予定オブジェクトが自動生成されます。

**代替タスクシステム**：タスクの前提条件が現在の状態で満たされない場合、期待状態の近さで候補をランク付けして代替タスクを提案します。

**通知システム**：標準時間判定、タイマー判定、センサー情報判定、ユーザー入力判定、状態遷移判定、LLM API判定の6種類の判定方法を組み合わせた柔軟な設計です。

**プログラムとLLMの使い分け**：プログラムによる自動評価を基本とし、複雑なケースや時系列パターン認識が必要な場合にのみLLM APIを使用する方針です。

### 3. データモデルに関する決定_2
このフォルダには方針転換に関する資料が含まれています。

**方針の転換.txt**：設計方針の変更点が記録されています。

**測定について.md**：測定に関する詳細な設計方針が記載されています。

**環境ネゲントロピー.txt**：環境エントロピーとネゲントロピーの計算方法について、掃除時間を物理量とした独自の定義が採用されています。部屋のエントロピーは基準掃除屋が完全に片付けるのに必要な期待掃除時間として定義され、ネゲントロピーは掃除によって減少したエントロピーの量として定義されています。

### 4. 状態リスト
`ユーザ状態.txt`には、標準状態、心理的抑制状態、起床時起立可能状態、作業開始可能状態、清掃開始可能状態、作業継続可能状態、作業時DMN活性状態、表現力状態、感受性状態、不安障害状態、過集中・覚醒など、具体的なユーザー状態の定義と判定条件が記載されています。

### **記号割り当てチャート**

#### **1. Group A: 物理定数・係数 (Physical Constants)**
*   **割り当て**: **ドミノ牌 [横向き] (Domino Tiles Horizontal)** `U+1F030` 〜
*   **理由**: ドミノの「点の数」は不変の数値を表すのに適しています。横向きは「静的で安定した定数」を表現します。
*   **分類 (現在の値: 13個 / 想定: 20個)**:
    *   **単位処理時間 $\tau$ (6個)**: 🀰(0-0) 〜 🀵(0-5)
    *   **物理係数・率 (7個)**: 🀶(0-6) 〜 🀼(1-6)

#### **2. Group B: システム設定・閾値 (System Settings)**
*   **割り当て**: **ドミノ牌 [縦向き] (Domino Tiles Vertical)** `U+1F062` 〜
*   **理由**: 同じ数値情報ですが、縦向きにすることで「ユーザーやシステムが設定した壁（閾値・リミット）」というニュアンスを持たせ、物理定数と区別します。
*   **分類 (現在の値: 12個 / 想定: 20個)**:
    *   **制限・リミット (4個)**: 🁠(0-0) 〜 🁣(0-3)
    *   **閾値・判定基準 (3個)**: 🁤(0-4) 〜 🁦(0-6)
    *   **設定・定義参照 (5個)**: 🁧(1-1) 〜 🁫(1-5)

#### **3. Group C: 動的状態変数 (Dynamic State Variables)**
*   **割り当て**: **麻雀牌 (Mahjong Tiles)** `U+1F000` 〜
*   **理由**: 麻雀牌は「萬子・筒子・索子・字牌」という種類（スート）を持ち、状態のカテゴリ分け（ユーザー、環境、社会など）に最適です。また、ゲームの進行とともに変化する「手牌」のイメージが動的変数に合致します。
*   **分類 (現在の値: 16個 / 想定: 30個)**:
    *   **状態オブジェクト (4個)**: 🀀(東:Current), 🀁(南:User), 🀂(西:Env), 🀃(北:Social)
    *   **エントロピー指標 (3個)**: 🀄(中:部屋S), 🀅(發:ネゲントロピーJ), 🀆(白:組織S)
    *   **能力・レベル (2個)**: 🀇(萬子1), 🀈(萬子2)
    *   **フラグ・確率 (4個)**: 🀙(筒子1) 〜 🀜(筒子4)
    *   **カウンタ (3個)**: 🀐(索子1) 〜 🀒(索子3)

#### **4. Group D: コンテナ・スキーマ (Containers & Schemas)**
*   **割り当て**: **罫線素片 (Box Drawing)** `U+2500` 〜
*   **理由**: データを格納する「箱」や「構造」を表すのに最適です。太線・細線・二重線でコンテナの種類を区別できます。
*   **分類 (現在の値: 9個 / 想定: 15個)**:
    *   **リスト・キュー (6個)**:
        *   リスト: ├ (List Item)
        *   キュー: ╏ (Vertical Queue)
    *   **スキーマ定義 (3個)**:
        *   構造体定義: ▦ (User), ▩ (Env) ※該当グリフがなければ太枠 `┏` 等で代用

#### **5. Group E: 演算子・関数 (Operators & Functions)**
*   **割り当て**: **矢印 (Arrows)** `U+2190` 〜
*   **理由**: 入力から出力への「変換」「作用」「方向」を表すのに矢印以上のものはありません。矢印の形状（二重、白抜き、破線）で関数の性質を分類します。
*   **分類 (現在の値: 19個 / 想定: 30個)**:
    *   **計算 (Calc系)**: → (通常矢印: 単純な計算)
    *   **判定 (Judge/Detect系)**: ⇒ (二重矢印: 論理的な帰結・判定)
    *   **検索・選択 (Find/Select系)**: ⇢ (破線矢印: 探索)
    *   **更新・変換 (Update/Convert系)**: ↻ (回転矢印: 状態更新) or ↝ (波線矢印: 変換)
