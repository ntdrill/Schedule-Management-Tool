## 本資料の範囲（v1/v2の境界）

### 資料準拠（事実）

- `v1`は「未来の計画（状態配置）」を行わず、**測定ON/OFF**と**対処行動の記録・評価**に特化したロガーとして定義されている。
- `v1`の実装対象は iOS/watchOS（Swift/SwiftUI/SwiftData または Core Data）で、HealthKit/SwitchBot 連携を前提とする。
- `v2以降`は「状態中心設計」に基づき、タイムライン上の状態配置・自動補完・Yes/No確認による実行フローを採用する（v1範囲外と明記）。

- 統合設計書内に「未整備」と明記された項目（タイムラインの時間ブロック配分、通知・アラート要件、データベース化・スコア化）は確定できない。

# 0. 理論的枠組み：形式的記述と知能の定義

本プロジェクトは、ソフトウェア工学、数理論理学、およびマルチエージェントシステムの理論に基づき、以下の公理的枠組みの上で設計・実装されている。

## 0.1. ソフトウェアの形式的記述
全てのソフトウェアシステム（対象システム）は、便宜性やダイナミクスを捨象することで、以下の二つの要素の集合として数学的に厳密に記述可能である。

1.  **定数（Statics）**:
    *   初期状態、不変の物理法則、データ構造の定義域（Domain）。
    *   例：状態空間の次元、崩壊係数、リソースの最大値。
2.  **変換（Transformations）**:
    *   ある状態を入力とし、別の状態を出力する写像（Map）。
    *   例：時間発展関数、ユーザー介入による状態遷移、タスク実行ロジック。

本プロジェクトでは、コードを「機能の羅列」ではなく、この「定数と変換の集合」として定義し、実装を行う。

## 0.2. 実装システムの二重性定理
システムが構成される時、それを構築する別のシステムが事前に（あるいは同時に）構築されなければならない。

*   **対象システム (Target System)**: ユーザーが利用する成果物（スケジュール管理ツール）。
*   **実装システム (Implementation System)**: 対象システムを構築するためのエージェント群、ワークフロー、ドキュメントの集合。

我々は「スケジュール帳を作る」だけでなく、それを生成する「実装システム」自体を設計・運用している。

## 0.3. 知能の定義
本アーキテクチャにおいて、「知能（Intelligence）」を以下のように定義する。

> **定義：あるシステムが、論理的構成に基づいて別の新たなシステムを構築できる能力を持つ時、その能力を知能と呼ぶ。**

エージェントとは、魔法のような自律存在ではなく、この「構築能力（論理分解力と写像実行力）」を特定のドメイン（物理計算、決済処理、言語生成など）に限定してカプセル化した機能単位である。

このシステムは「状態（定数）」と「変換（状態遷移）」の集合として形式的に記述される。すべての動作フローは、現在の状態に変換を適用して次の状態を得る、という枠組みで理解できる。状態と変換はシンボル言語で表現され、シンボルは `data/constants.txt`, `data/variables.txt`, `data/transforms.txt` およびSupabaseの `symbols` テーブルで管理されている。

## 0.4. 記号的記述の理論：編み図メタファーと構造表現

本システムの形式的記述において、なぜ1文字のUnicode記号を採用するのか。その理論的背景には、**編み図（Knitting Charts）**のメタファーがある。

### 1. 編み図のアナロジー
編み図は、1つの記号の中に「表編み」「掛け目」といった具体的な**手続き（Operation）**の情報と、糸の**入出力の順序（IO Order）**、そして**展開（Expansion）**の情報が内包されている。
これらの記号が連結されることで、2次元の平面記述から、複雑な3次元トポロジー（立体構造）が厳密に再現される。

### 2. 自由な方向性と連結性
1文字の記号は、通常の文字列のような線形性（Linearity）から解放され、**自由な向き（Directionality）**を持つことができる。
この特性により、ファイルシステムや関数呼び出しの複雑な依存関係（グラフ構造）を、従来のコード記述よりも高い**解釈可能性（Interpretability）**と**表現力（Expressiveness）**を持って記述できる。

### 3. 厳密性と解釈可能性の両立
この記号体系は、以下の要素を同時に満たすことを目的としている。
- **構成規則・代入規則・推論規則**：数学的に保証された厳密なルール。
- **解釈可能性**：人間が直感的に構造や流れを理解できる視覚的表現。

将来的に、この記述法は人による高い表現能力と、システムによる厳密な解釈を両立させる基盤となる。

# 1. 状態中心設計（v2以降）

## 資料準拠（事実）

- ユーザーは「何をするか」ではなく「どのような状態でありたいか」だけを指定する。
- タスク選択、測定タイミング、チェックリスト提示は、指定状態に基づきシステムが自動補完する。
- タイムラインは DAW ライクな並列トラックで、**ユーザー状態・環境状態・社会的状態**の3トラックを配置する。
- 実行段階では「現在その状態か」を Yes/No で確認し、No の場合は介入（代替行動）を提案する。
- 外部予定は「想起している状態」として状態オブジェクト化し、測定は「測定している状態」として扱う。

# 2. 状態管理の基本構造
著：user_state_agent

### 資料準拠（事実）: 最低限の共有事項

**1. ユーザ状態の3層構造**

| 層 | 定義 | 役割 |
|---|---|---|
| 現在のユーザー状態オブジェクト | 最新状態を保持する単一インスタンス | 前提条件チェック、危篤状態検知の基準 |
| 状態スキーマ | 期待状態や前提条件を記述する設計図 | タスクの期待状態、前提条件の定義（部分的定義可） |
| 状態履歴オブジェクト | 特定時点のスナップショット | 時系列分析、効果測定の基礎データ |

**2. 3層の連携フロー**
1. **計画時**: 状態スキーマで期待状態（expectedState）を定義
2. **実行前**: 現在のユーザー状態で前提条件をチェック
3. **実行時**: 現在状態をスナップショット保存（actualStateBefore）
4. **実行後**: 完了時状態をスナップショット保存（actualStateAfter）し、期待状態と比較評価

**3. 状態管理対象の一般化（subjectType）**
- `user`（ユーザー状態）、`environment`（環境状態）、`social`（社会的状態）
- 各subjectTypeは独立したオブジェクトとして管理
- 環境状態・社会的状態の詳細は第10章・第11章を参照

**4. 状態の更新トリガー（4種類）**
- センサー自動更新（HealthKit等）
- チェックリスト回答
- ユーザー手動入力
- タスク実行後の記録

**5. 状態の部分的定義**
- 状態スキーマはすべてのフィールドを指定する必要がない
- タスクで重要なフィールドだけを指定できる（ユーザーの入力負荷軽減）
- センサー自動取得データは常に記録、ユーザー入力はexpectedStateで指定されたもののみ

**6. 期待状態と実際状態の構造**
- `stateBefore` / `stateAfter` は `{expected: <スキーマ>, actualId: <履歴オブジェクトID>}` 構造
- 比較結果は `evaluationResult` として `matchScore (0-1)` と `fieldDetails` で構造化

**7. 測定能力との関係（最低限の言及）**
- ユーザーの認知リソースが枯渇すると、状態を正確に把握する能力（測定能力）が低下する
- 測定能力が低下すると、現状認識→計画→実行の流れが破綻する
- **したがって、システムは状態記録を強制せず、認知コストに配慮した設計とする**
- 詳細は第6章「測定」を参照

**8. 危篤状態とリカバリー**
- 危篤状態：通常の閾値を超えた異常な状態
- 検知時はリカバリータスクを優先的に提示
- v1では手動で対処行動を選択・記録
- v2以降はルールベース判定とLLM判定を併用

### 詳細な情報を必要とする場合

以下のトピックについては、**User_State_Agent** に問い合わせてください：

| トピック | 概要 |
|---------|------|
| 状態フィールドの詳細 | 神経、脈拍、行動、想起等の意味・計測方法・閾値 |
| 危篤状態の判定ロジック | どの値がどの閾値を超えると危篤とみなすか |
| 状態プリセット | 「標準」「作業開始可能」「集中」等の設計意図 |
| 状態の比較評価の詳細 | matchScoreの計算方法、重み付けロジック |
| 状態空間と状態ベクトル | 状態の多次元ベクトル表現、次元対応 |
| 状態とエントロピーの関係 | 分散、ネゲントロピー、環境→ユーザーの因果連鎖 |

# 4. 予定オブジェクトと実行オブジェクト
担当:data_model_agent
### 資料準拠（事実）

- **予定オブジェクト**は不変のスケジュール意図、**実行オブジェクト**は実績の記録として分離される。
- 予定は `scheduledStart/scheduledEnd` を持ち、実行は `actualStart/actualEnd` を持つ。
- 予定の `status` は `scheduled/cancelled`、実行の `status` は `in_progress/completed/skipped/failed/interrupted`。
- テンプレートとインスタンスの二層構造を採用し、同一テンプレートの履歴抽出を可能にする。

担当：user_state_agent

# 6. 測定（Measurement）
担当：monitoring_state_agent

### 資料準拠（事実）: 最低限の共有事項

**1. 測定モードの存在**
- 測定状態（ON）と非測定状態（OFF）がある。
- 測定状態は独立した予定オブジェクト（`type=measurement_session`）として扱う。
- 推奨量: 日次6〜8時間、週3〜6回。

**2. 測定の広義の定義**
- 「測定」はセンサーデータに限らない。
- メタ認知、脈を触る、感情の言語化、セーバリングなど、**自己の状態を把握・確定するあらゆる行為**を含む。

**3. 測定能力と実行機能の因果関係**
- 測定能力（自己の状態を把握できる能力）が低下すると、現状認識→計画→実行という流れが破綻し、タスク遂行能力も低下する。
- **これがシステム設計の根幹にある前提**である。

**4. 環境との因果関係**
- 環境エントロピーが高い（散らかっている）と、測定能力が低下する。
- したがって、**環境管理は測定保護の手段**でもある。

**5. システムの役割**
- このシステムは、ユーザーの**自己監視能力の拡張・補完**を目的とする。
- センサーによる自動記録、チェックリスト、介入提案などは、すべて「測定を支援する」ための仕組みである。

**6. 測定の保護原則**
- 測定には認知コストがかかり、継続すると疲労する。
- **無理に測定を続けるとドロップアウト（システム離脱）を招き、逆効果となる**。
- システムは測定を強制せず、非測定状態（休息）を明示的に設計している。

### 詳細な情報を必要とする場合

以下のトピックについては、**Monitoring_State_Agent** に問い合わせてください：

| トピック | 概要 |
|---------|------|
| 測定品質の評価 | 品質スコア、有効性閾値、継続性判定 |
| 測定疲労・認知リソース | 動的管理、ドロップアウト予測の計算 |
| 主観と客観の乖離 | 乖離スコア、解離検知、介入レベル |
| 測定資源 | 内部資源と外部資源の分類 |
| 組織エントロピー | 相互測定エッジ、測定能力低下の社会的影響 |

| 具体的なユースケース | デバイス未装着検知、データ補完など |

# 8. 代替タスクの原理

### 資料準拠（事実）

- 前提条件が満たされない場合、`expectedStateAfter` の近さで代替タスクを検索する。
- 近さの評価はフィールド一致数や重み付け一致率で行う。
- 適切候補がない場合は LLM による推奨へ移行する。

# 13. 対処行動と場面データ

### 資料準拠（事実）

- `coping_actions` は **78項目**、`coping_scenarios` は **221項目**を登録する設計。
- 行動は `measurement/physical/nutrition/psychological/audio/tool/other` に分類される。
- 場面は `physical/mental/cognitive/behavioral` に分類される。
- 効果・手軽さ・おすすめ度などの評価フィールドが存在する。
