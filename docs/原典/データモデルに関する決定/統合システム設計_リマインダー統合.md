# セルフマネジメント × リマインダーツール 統合設計書

## 資料準拠（既存フレームワークの整理）

### 既存システムの核となる概念
- **状態オブジェクト**: 行動/想起/栄養/目標/神経/臓器/筋肉/血圧/脈拍/測定の値の組合せで状態を定義。
- **測定状態/非測定状態**: 測定推奨は1日6〜8h、週3〜6回。心理的負荷を管理。
- **チェックリスト**: 時間単位（即時/セッション/朝夜/日次/週次/月次）× 観点でチェック項目を配置。
- **危篤状態→安全状態のリカバリー**: 状態遷移として対処プロセスを表現。
- **タイムラインテンプレート**: 24h の状態分布を規定、バッファ2h/日確保（未整備）。
- **将来構想**: スマートウォッチをインターフェースに、状態フローを可視化・通知。

### 既存資料での未整備項目（資料明記）
- タイムラインの時間ブロック配分（睡眠/深作業/浅作業/運動/食事/バッファ）。
- 状態オブジェクトのスキーマ詳細（ID/作成時刻/タグ/ソース）。
- 通知・アラートの具体要件（当面は手動運用）。
- データベース化・スコア化（当面見送り）。

## リマインダーツール要件（ユーザー提示）

### 必須機能
1. **クロスプラットフォーム対応**: iOS/Windows/ブラウザで共通の通知・同期。
2. **タスクテンプレート機能**: 不定期タスクを登録・再利用。
3. **ドラッグ＆ドロップ操作**: 分単位でカレンダーにタスクブロックを配置。
4. **通知・リマインダー**: プッシュ/デスクトップ通知でタスク実行をリマインド。
5. **AI自動スケジューリング（将来）**: 蓄積データから最適スケジュールを提案。
6. **日本語UI**: 直感的な操作性。

## 統合設計（提案/ドラフト）

### 設計方針
1. **状態オブジェクトとタスクテンプレートの統合**: 
   - タスクテンプレートは「行動」を中心とした状態オブジェクトのサブセット。
   - 各テンプレートに「期待される状態遷移」を紐づけ、危篤状態→安全状態のリカバリープロセスと連携。

2. **チェックリストと通知の統合**:
   - チェックリストの各項目にトリガー条件（時刻/状態変化/閾値）を設定可能に。
   - 通知は「測定状態への移行促進」「危篤状態の検知」「目標の再認識」の3種に分類。

3. **タイムライン = スケジュール + 状態フロー**:
   - カレンダーUIで配置されるタスクブロックは、同時に状態オブジェクトとして記録。
   - 実行後は実績として蓄積し、AI学習データに利用。

4. **測定負荷の管理**:
   - 測定状態（1日6〜8h）の枠内でのみ詳細な状態記録・通知を有効化。
   - 非測定状態では最小限の通知（緊急介入のみ）。

### 技術スタック候補（提案）

#### バックエンド
- **言語・フレームワーク**: Node.js (TypeScript) + Express/Fastify、または Python (FastAPI)
- **データベース**: 
  - PostgreSQL (構造化データ: タスク/状態オブジェクト/チェックリスト)
  - TimescaleDB拡張 (時系列データ: 状態履歴/バイタル測定値)
  - Redis (リアルタイム同期キャッシュ)
- **認証・同期**: Supabase または Firebase (クロスプラットフォーム同期、認証、リアルタイムDB)

#### フロントエンド
- **Web**: React + Next.js (TypeScript) + Tailwind CSS
  - カレンダーUI: `react-big-calendar` または `FullCalendar`
  - ドラッグ＆ドロップ: `react-dnd` または `dnd-kit`
- **iOS**: SwiftUI (ネイティブ) + Combine
- **Windows**: 
  - オプション1: Electron (Web技術の流用)
  - オプション2: .NET MAUI (ネイティブパフォーマンス)

#### 通知
- **プッシュ通知**: 
  - iOS: APNs (Apple Push Notification service)
  - Web: Web Push API
  - Windows: Windows Notification API または Electron の Notification
- **通知管理**: Firebase Cloud Messaging (統一インターフェース)

#### AI機能（将来）
- **推論エンジン**: Python (scikit-learn/TensorFlow/PyTorch)
- **特徴量**: 
  - タスク完了時刻・所要時間の履歴
  - 状態オブジェクトの遷移パターン
  - チェックリスト充足率
  - 危篤状態の発生頻度・時間帯
- **最適化目標**: 
  - 測定負荷を6〜8h/日に収める
  - 危篤状態の発生を最小化
  - バッファ2h/日を確保
  - 目標達成率を最大化

## データモデル（提案）

### 1. TaskTemplate（タスクテンプレート）

```typescript
interface TaskTemplate {
  id: string;
  title: string;  // 例: "太極拳", "YouTube制作", "食事準備"
  description?: string;
  
  // 既存の状態オブジェクトとの統合
  stateSignature: {
    行動: string[];  // 辞書.yamlの値から選択
    想起?: string[];
    栄養?: string;
    目標?: string;
  };
  
  // スケジューリング属性
  defaultDuration: number;  // 分単位
  color: string;  // カレンダー表示色
  category: 'work' | 'exercise' | 'meal' | 'communication' | 'recovery';
  
  // 通知設定
  reminderOffset?: number;  // タスク開始の何分前に通知
  checklistItems?: string[];  // このタスク用のチェック項目ID
  
  // 頻度情報（統計用、強制ではない）
  typicalFrequency?: {
    count: number;
    period: 'day' | 'week' | 'month';
  };
  
  createdAt: Date;
  updatedAt: Date;
}
```

### 2. TaskInstance（スケジュール配置されたタスク実体）

```typescript
interface TaskInstance {
  id: string;
  templateId: string;  // TaskTemplateへの参照
  
  // スケジュール
  scheduledStart: Date;
  scheduledEnd: Date;
  actualStart?: Date;  // 実績
  actualEnd?: Date;
  
  // 状態記録
  stateBefore?: StateObject;  // タスク前の状態
  stateAfter?: StateObject;   // タスク後の状態
  
  // ステータス
  status: 'scheduled' | 'in_progress' | 'completed' | 'skipped' | 'cancelled';
  completionNote?: string;
  
  // 通知履歴
  notificationSent: boolean;
  notificationAcknowledged: boolean;
  
  // 測定管理
  isMeasuredSession: boolean;  // 測定状態内のタスクか
  
  createdAt: Date;
  updatedAt: Date;
}
```

### 3. StateObject（既存定義の拡張）

```typescript
interface StateObject {
  id: string;
  userId: string;
  
  // メタ
  title: string;
  purpose?: string;
  timestamp: Date;
  isMeasured: boolean;  // 測定状態か非測定状態か
  
  // 値（辞書.yamlから選択）
  行動: string[];
  想起: string[];
  栄養?: string;
  目標?: string;
  神経?: string;
  臓器?: string;
  筋肉?: string;
  血圧?: string;
  脈拍?: string;
  
  // 拡張（提案）
  source: 'manual' | 'task_completion' | 'checklist' | 'auto_sensor';  // 記録のソース
  taskInstanceId?: string;  // 関連タスク
  tags?: string[];
  confidence?: number;  // 主観確信度 (0-1)
  evidence?: string;  // 測定/所見の出典
  
  // 危篤状態との関連
  criticalState?: string;  // 危篤状態名（該当する場合）
  isSafeState: boolean;  // 安全状態に到達しているか
  
  note?: string;
  createdAt: Date;
}
```

### 4. Checklist（チェックリスト定義）

```typescript
interface ChecklistDefinition {
  id: string;
  title: string;
  timing: 'immediate' | 'session' | 'morning' | 'evening' | 'daily' | 'weekly' | 'monthly';
  items: ChecklistItem[];
}

interface ChecklistItem {
  id: string;
  question: string;  // 例: "呼吸できるか"
  examples?: string[];  // 具体例
  purpose: string;  // 目的
  
  // 通知トリガー（提案）
  triggerCondition?: {
    type: 'time' | 'state_change' | 'task_start' | 'task_end';
    value?: any;
  };
  
  // 評価基準
  expectedValue?: string;  // 期待される回答/状態
  threshold?: any;  // 閾値（数値の場合）
}

interface ChecklistInstance {
  id: string;
  definitionId: string;
  userId: string;
  timestamp: Date;
  responses: {
    itemId: string;
    answer: any;  // boolean, string, number等
    note?: string;
  }[];
  associatedTaskId?: string;
  associatedStateId?: string;
}
```

### 5. NotificationRule（通知ルール）

```typescript
interface NotificationRule {
  id: string;
  userId: string;
  
  type: 'task_reminder' | 'checklist_prompt' | 'state_alert' | 'measurement_limit';
  
  // トリガー
  trigger: {
    condition: string;  // 例: "measurement_hours_today >= 8", "critical_state_detected"
    parameters?: Record<string, any>;
  };
  
  // 通知内容
  title: string;
  message: string;
  priority: 'low' | 'medium' | 'high' | 'urgent';
  
  // 配信設定
  deliveryChannels: ('push' | 'desktop' | 'watch')[];
  
  // 有効時間
  activeHours?: { start: string; end: string; };  // 例: "09:00"-"21:00"
  activeDays?: number[];  // 0=日曜, 1=月曜...
  
  enabled: boolean;
  createdAt: Date;
}
```

### 6. MeasurementSession（測定セッション管理）

```typescript
interface MeasurementSession {
  id: string;
  userId: string;
  date: Date;  // 日付
  
  sessions: {
    startTime: Date;
    endTime?: Date;
    durationMinutes?: number;
    taskIds: string[];  // このセッション中のタスク
    stateIds: string[];  // このセッション中の状態記録
  }[];
  
  totalMeasuredMinutes: number;
  targetMinutes: number;  // 目標（例: 360-480分 = 6-8h）
  
  weeklyTotal?: number;  // その週の累計（週3-6回管理用）
  
  createdAt: Date;
}
```

## 統合ワークフロー例

### シナリオ: 朝のルーティン

1. **起床（7:00）**
   - 自動通知: "起床時チェックリスト"
   - ユーザーがチェック項目に回答 → StateObject記録（神経/筋肉/測定=是）

2. **太極拳タスク（8:00-8:30）**
   - 7:50に通知: "10分後: 太極拳"
   - ユーザーがタスク開始ボタンをタップ → タスク前の状態を記録
   - 8:30に完了 → タスク後の状態を記録（想起: "ゆっくり動くと頭が冴える"）
   - システムが状態変化を検出: 解離感 → 解離感解消

3. **YouTube制作（9:00-11:00）**
   - カレンダーから事前にドラッグ＆ドロップで配置済み
   - 9:00に通知
   - 作業中、1時間ごとに「セッション中チェックリスト」（筋緊張/集中度）
   - 測定時間カウンター: 3.5h / 8h

4. **測定上限アラート（15:00）**
   - システム検知: 測定時間が8hに到達
   - 通知: "今日の測定時間が目標に達しました。非測定モードへの移行を推奨します"
   - ユーザーが承認 → 以降、詳細通知は最小限に

### シナリオ: 危篤状態の検知と対処

1. **状態悪化の検知（22:00）**
   - 就寝前チェックリストで「過覚醒」を検出
   - システムが危篤状態として記録
   - リカバリー提案: "対処方法: 呼吸を30回する、マッサージガン"

2. **リカバリータスクの自動提案**
   - システムが過去データから有効だった対処行動を提示
   - ユーザーが「呼吸法30回」タスクを即配置（10分）
   - 完了後の状態記録 → 過覚醒 → 入眠準備完了（安全状態）

## 技術的考慮事項（提案）

### 1. データ同期戦略
- **リアルタイム同期**: Supabase Realtime または Firebase Realtime Database
- **競合解決**: Last-Write-Wins（LWW） + タイムスタンプベースのマージ
- **オフライン対応**: ローカルSQLite（iOS/Windows）+ 再接続時の差分同期

### 2. 通知の一貫性
- **統一ペイロード**: 各プラットフォームの通知APIをラップする共通レイヤー
- **配信確認**: 通知送信履歴DBで重複防止
- **ユーザー設定**: 通知ON/OFF、時間帯制限、優先度フィルター

### 3. パフォーマンス
- **カレンダーUI**: 仮想スクロール（数千件のタスクでも高速）
- **状態履歴クエリ**: TimescaleDBで時系列データを高速集計
- **キャッシュ戦略**: Redis（セッション/よく使うテンプレート）

### 4. セキュリティ
- **認証**: OAuth 2.0（Google/Apple Sign-In）
- **データ暗号化**: 転送時（TLS）+ 保管時（AES-256）
- **アクセス制御**: Row Level Security（RLS）でユーザーごとのデータ分離

### 5. 拡張性
- **マイクロサービス化（将来）**: AI推論エンジンを独立サービスに
- **Webhook**: 外部ツール連携（Google Calendar、Notion等）
- **プラグインシステム**: カスタム状態カテゴリの追加

## リスクと対策（提案）

### リスク1: クロスプラットフォーム同期の複雑性
- **対策**: 初期はWeb版のみでMVP検証。同期ロジックを最初から設計に組み込む。

### リスク2: 測定負荷の管理が形骸化
- **対策**: 測定時間の可視化を常に前面に。上限アラートを必須機能に。

### リスク3: AI提案の精度不足
- **対策**: Phase 4は最後に配置。手動運用で十分なデータ蓄積後に着手。

### リスク4: ユーザー（作成者本人）の継続利用
- **対策**: 
  - 短期目標（YouTube投稿・収益化）と直結する機能を優先
  - 測定負荷を超えない設計（週3-6回、1日6-8h）
  - 非測定日も罪悪感なく使える「非測定モード」の明示
